# Domain – Request: Request

**Project:** Tiferet Framework  
**Repository:** https://github.com/greatstrength/tiferet  
**Date:** August 09, 2026  
**Version:** 2.0.0

## Overview

`Request` is the declared, immutable shape of the inputs to a single feature execution — session, feature, headers, and data — kept deliberately separate from the mutable runtime state (the in-progress `result`) that accumulates while a feature's steps execute. This split is why a `Request` is a plain `DomainObject` while its execution-time counterpart, `RequestContext` (`tiferet/contexts/request.py`), is a `BaseContext` that binds a `Request` as `self.domain` and layers `result` on top as context-only state.

**Module:** `tiferet/domain/request.py`
**Vision:** See the `Request` class docstring in `tiferet/domain/request.py` for the value statement this guide distills.

## Ubiquitous Language

- **Session id** — `Request.session_id`, a `uuid4` string auto-generated by `derive_session_id` when not supplied; unrelated to `AppSession.id` (an `AppSession` is a declared application entry point, not a per-request identifier).
- **Runtime result** — the in-progress or final output of a feature execution. Deliberately **not** a `Request` field; it lives only on `RequestContext.result`.
- **Proxy property** — a `RequestContext` property (`session_id`, `feature_id`, `headers`, `data`) that reads and writes straight through to the bound `Request` domain object rather than holding its own state.

## Domain Objects

### Request

A request value object carrying the session, feature, headers, and data for a single feature execution.

| Attribute | Type | Required | Default | Description |
|---|---|---|---|---|
| <a id="request-session-id"></a>`session_id` | `str` | Yes | auto-generated `uuid4` | The unique session identifier for the request. |
| <a id="request-feature-id"></a>`feature_id` | `str \| None` | No | `None` | The identifier of the feature being executed. |
| <a id="request-headers"></a>`headers` | `Dict[str, str]` | No | `{}` | The request headers. |
| <a id="request-data"></a>`data` | `Dict[str, Any]` | No | `{}` | The request data payload. |

No methods — `Request` is a pure data container. All read/write access at runtime goes through `RequestContext`'s proxy properties instead of the domain object directly.

#### Derivation

<a id="request-derive-session-id"></a>
**Session ID Derivation via `@model_validator`**

`derive_session_id` generates a `uuid4` string for `session_id` when one is not supplied, mirroring the derivation validators on other domain objects (e.g. `Error.error_code`, `CliCommand.id`):

```python
req = Request(feature_id='calc.add', data={'a': 1, 'b': 2})
# req.session_id is a freshly generated uuid4 string
```

## Relationship to RequestContext

`Request` and `RequestContext` intentionally split declared input from runtime state:

- `RequestContext.__init__` builds and binds a `Request` from the supplied constructor arguments (`headers`, `data`, `session_id`, `feature_id`), then separately initializes `self.result = None`.
- Each of `session_id`, `feature_id`, `headers`, and `data` is exposed on `RequestContext` as a read/write **proxy property** that delegates straight to `self.domain` — there is no duplicated state between the context and the bound `Request`.
- `RequestContext.set_result(result, data_key=None)` writes either into `self.result` directly or into `self.domain.data[data_key]`, depending on whether the executing step declared a `data_key`.
- `RequestContext.handle_response()` returns `self.result` by default; subclasses (e.g. a Flask-specific context) can override it to shape the final response differently.

```python
from tiferet.contexts.request import RequestContext

ctx = RequestContext(feature_id='calc.add', data={'a': 1, 'b': 2})
ctx.session_id       # proxied to ctx.domain.session_id
ctx.set_result(3)    # ctx.result == 3 (no data_key)
ctx.handle_response() # 3
```

## Boundaries

**Inside this domain:** the declared, immutable shape of a feature execution's inputs (session, feature, headers, data) and the session-id auto-derivation.
**Outside this domain:** the mutable runtime `result` and the read/write proxy properties (`RequestContext`, `docs/core/contexts.md`); request-schema validation and coercion against a `Feature.params_schema` (`RequestSpecification`, [docs/guides/domain/feature.md](feature.md)) — a `Request`'s `data` is validated by that separate mechanism, not by `Request` itself.

## Instantiation

```python
from tiferet.domain import Request

req = Request(
    feature_id='calc.add',
    data={'a': 1, 'b': 2},
)
# req.session_id is auto-generated; req.headers == {}
```
